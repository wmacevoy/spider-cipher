Why a visible cipher?

Invisible magic

You can’t watch it

Modern ciphers are unintelligible to almost everyone and impossible to observe in action.

Time

Technology ages fast

Will your heirs be able to decode your keys in 100 years? Cards and arithmetic will still work.

Trust

Who do you trust?

Hardware and apps can be compromised. A deck of cards on a table can be audited.

By hand with a deck of cards, or by computer.
Either way, 40! ≈ 2159 possible keys.

From the original deck: modern ciphers are invisible magic; technology ages fast (cryptocurrency keys and heirs); trust (root-kits, man-in-the-middle, hardware back doors). Spider is doable by hand with cards, some dice, and two-digit arithmetic, and it is a concrete example of a modern stream cipher. You can use a computer, but you don’t have to.

The whole system

Once

Share a shuffled deck in secret. Its order is the key.

For every message

1 · Translate

Text → cards, with shift cards for capitals, digits, and symbols.

→

2 · Packet

Add random cards before and between the message cards.

→

3 · Scramble

Add noise from the deck to each card, moving the deck as you go.

To read a message, do the reverse: unscramble, unpacket, detranslate.

Keep the three stages separate in people’s minds: translate is a public encoding (no secret), packet adds randomness (so the same message never scrambles the same way twice), and scramble is the only step that uses the key.

40 cards as the numbers 00 to 39

Queen = 0 (a Q looks like a 0), Ace = 1, then 2 to 9. Suits in alphabetical order give the tens digit.

Take the Q, A, 2–9 of each suit from a standard deck: 40 cards. Clubs are 00–09, diamonds 10–19, hearts 20–29, spades 30–39 (alphabetical: clubs, diamonds, hearts, spades). Kings, jacks and tens are unused; laying the kings out in suit order makes a handy reference.

Mod 40 arithmetic

Add ⊕

9♦ ⊕ 2♠
= 19 + 32 = 51
≡ 11 = A♦

Subtract ⊖

9♦ ⊖ 2♠
= 19 − 32 = −13
≡ 27 = 7♥

Add or subtract 40 until the result is in 00 to 39. Shortcut: 32 + 8 = 40, so ⊕ 32 is the same as ⊖ 8.

Card arithmetic is clock arithmetic with 40 hours. Practice: 19 ⊕ 32: 19 − 8 = 11. 19 ⊖ 32: 19 + 8 = 27. Everyone should do two or three of these before scrambling anything.

Translate: one card, three meanings

Big: normal · left: shifted up · right: shifted down · ␣ space, ⏎ new line

Each card 00–35 means one character in each of three shift states: normal (lower case, space and punctuation), up (capitals and brackets), and down (digits, hex A–F, symbols). Spades 6–9 (36–39) change state: ↓ shift down and ↑ shift up for the next character only; ⤓ lock down and ⤒ lock up until changed. 34 and 35 are emoji: 👎 👍 normal, 💔 ❤ up, 😢 😄 down. This is the table in src/spider_cipher.c (CODES, UP_CODES, DOWN_CODES).

Start normal

Every message starts in the normal state.

↑ ↓ one shot

Shift for the next character, then come back.

⤒ ⤓ lock

Stay in the new state until the next shift card.

Anything else

Below down: the character’s code point in hex, cards 00–15.

Example: “café” → c a f ⤓ ⤓ E 9 ⤒ — two locks down to hex, then é = U+00E9.

The encoder looks ahead (up to ten characters) to choose the state that covers the most text, and locks when a run is longer than one character. After a hex character it writes ⤓ if another hex character follows, otherwise ⤒ back to the down state. The example is exactly what the reference encoder produces: 02 00 05 38 38 14 09 39, then end-of-message cards.

Translate it yourself

Type anything: the cards update live. Blue chips are shift cards, purple are hex digits, dashed are the end-of-message ⤒ cards. The message ends with at least five ⤒ (39), more until the length is a multiple of 10. The original slides hand-encode “#SPIDER Cipher.” as ↓ # ⤒ S P I D E R ⤓ ␣ ↑ C i p h e r . (36 20 39 18 …); the program finds a different but equally valid path (38 20 39 39 …). Any path decodes the same way.

M · message

The translated cards, ending with five or more ⤒ so the count is a multiple of 10.

A · ten random

Ten random cards in front. They stir the deck before any message card.

B · one before each

A random card before every message card.

Packet length = 10 + 2 × (message length): always a multiple of 10. The same message never scrambles the same way twice.

Random cards: draw from a second shuffled deck, roll dice, or use a computer. Change from the original slides: the reference code rounds the message itself up to a multiple of 10 with ⤒ cards (at least five), instead of adding random C cards at the end. The B cards are scrambled like everything else; the decrypter writes them to a separate “deniable” channel, so they can carry a second message.

Sorted deck 00…39: third card 02, tag 01, the card after 01 is 02, cut = 00 ⊕ 23 = 23. Reversed deck 39…00: third card 37, tag 36, the card after 36 is 35, cut = 39 ⊕ 23 = 62 ≡ 22. Both examples are checked against the reference code.

Scramble one card

1

Noise

Tag = third ⊖ 1; noise = the card after the tag.

2

Add

Scrambled = clear ⊕ noise. Write it down.

3

Cut

Cut card = first ⊕ clear. Cut it to the front.

4

Shuffle

Back-front: front card to back, front card to front, repeat.

Unscramble

Clear = scrambled ⊖ noise, then the same cut (using the clear card) and shuffle.

Arrange the key deck face up; for each packet card do 1–4; sort the deck when finished. Note: the original slides describe an older step (cut on the tag card, shuffle, then cut on the cut card). The current reference code (src/spider_cipher.c deckAdvance, and core/) cuts once, on first ⊕ clear, then shuffles; that is what these slides and demos use.

Reading a message

1 · Unscramble

Start from the key deck. Clear = card ⊖ noise; cut and shuffle.

→

2 · Unpacket

Drop the first ten cards, then every other card.

→

3 · Detranslate

Read cards with the shift table until five ⤒ in a row. No five ⤒? The packet was changed, or the key is wrong: reject it.

Same key deck

Both sides start every message from the key deck.

Lockstep

The cut uses the clear card, which the reader has just recovered.

Done

Sort the deck when finished, so the key isn’t left lying on the table.

Unpacket order matters: drop the ten prefix cards, then every other card starting with the first (those are the random B cards), then stop at the first run of five ⤒. Any ⤒ that happen to appear after the end are ignored. The run of five ⤒ is also the check: a changed card puts the decks out of step, so the run never comes, and the reader rejects the packet (REQ2/PK-2), except by chance about once in 405 tries. bin/spider_cipher does not act on this yet; see QUEUE item 11.

Making a key

By hand

Shuffle and copy

Shuffle thoroughly and write down the order, or make two decks in that order. 40! ≈ 2159 possible keys.

From a passphrase

Scramble a phrase

Start with a sorted deck and scramble the translated passphrase through it. The deck you end with is the key.

The command-line tool uses the passphrase method: spider_cipher --key='…' --encrypt='…'

A passphrase key is only as strong as the passphrase; a well-shuffled deck carries the full 159 bits. The passphrase method is DeckKey in src/spider_cipher_main.c: deckInit, then encode the key text (including its end-of-message cards) through the scramble step, discarding the output.

Try it

Encrypt runs translate, packet (with fresh random cards each time) and scramble; the output is in the same format as bin/spider_cipher (groups of five, rows of twenty), and the tool accepts its output in either cards or decimal format. Paste a packet from the command line to decrypt it here, or the other way around. Change one card in the packet and watch the rest of the message fall apart: the five ⤒ never arrive, which is how the reader knows it was changed.
